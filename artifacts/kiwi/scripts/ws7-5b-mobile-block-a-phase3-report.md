## Decisions made under "Auto Mode"

1. **New screen path: `/wizard-plan-details` (flat, sibling of `wizard-results`).** Considered `/wizard/plan-details` but `app/wizard.tsx` (input screen) and `app/wizard/` would conflict in expo-router. The flat naming matches the established pattern.
2. **`candidateContext` for the Tell Kiwi path: plumb the form input through.** The prompt mentions the wizard-results half of D-WS7-059. Set-Prefs already carries its input; Tell Kiwi did not. Plumbing `tellKiwiInput` keeps both paths real (rather than a stub default). `difficulty` defaults to `"medium"` on the Tell Kiwi path since `TellKiwiInput` has no difficulty field (free-text scenario); the AI expand prompt uses difficulty as a soft hint only.
3. **Decider helper rather than inline branching in the screen.** Pure-helper testability covers the load-bearing 404 dead-tap path without rendering the screen.
4. **Save success keeps user on Plan Details (no toast).** Hans's locked ruling; the saved state is communicated by the save button flipping to a "Saved to My Plans" badge with a check icon. No toast component exists in the codebase today (verified in WS7-4-D Ruling 9 — `Alert.alert` is the established fallback), so a screen-local badge avoids adding a new component for a single-shot confirmation.
5. **Daily averages aggregator** ([wizard-plan-details.tsx:77-95](artifacts/kiwi/app/wizard-plan-details.tsx#L77-L95)) sums per-dish per-serving macros across all dishes, divides by `meals.length` (= days). Skips `failed:true` and missing-macros dishes. The expanded payload doesn't carry plan-level rolled-up macros, so this is derived client-side; an inaccurate fallback would have been misleading.
6. **`/wizard-plan-details` overlay-style §5.4 modal lives on `wizard-results.tsx`, not as a separate component.** The state is local to the source screen (only fired from the candidate cards) and the prompt's "cancel = return to Results cards" semantic makes co-location the natural fit.
